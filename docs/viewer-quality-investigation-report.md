# SVRaster WebGL 모델 뷰어 화질 조사 리포트

> 작성 기준일: 2026-07-23
> 대상 모델: `iter020000_model.pt` / `iter020000_model.ply`
> 대상 장면: bonsai, 복셀 4,754,506개, SH degree 3

## 1. 한 줄 결론

현재 PLY 파일에는 원본 PT의 **위치와 SH 색상 계수가 거의 그대로 저장되어 있지만**, 현재 WebGL 뷰어의 렌더링 방식이 원본 SVRaster 렌더러와 다르기 때문에 원본 PT 렌더만큼 선명한 화질이 나오지 않는다.

따라서 지금까지의 결과만 놓고 보면 다음과 같이 판단하는 것이 정확하다.

- **확인된 사실:** PLY로 옮긴 위치와 SH 계수 자체는 크게 손실되지 않았다.
- **확인된 문제:** 현재 WebGL 결과는 흐리고, 꽃 부분에 세로 줄 또는 깨짐이 보이며, 장면에 검은 크랙과 색상 문제가 나타난다.
- **가능성이 낮아진 원인:** SH degree, 단순 샘플 수, 광선 교차 계산, 거리 정렬 방식만의 문제.
- **가장 유력한 원인:** 원본과 다른 복셀 정렬 및 픽셀 합성 방식.
- **제품 관점 결론:** 현재의 `PLY + WebGL2 instanced cube` 방식은 원본 품질을 보장하는 완성형 뷰어가 아니라, 근사 렌더링을 하는 프로토타입에 가깝다.

## 2. 먼저 알아야 할 용어

### PT 파일

학습된 SVRaster 모델의 원본 체크포인트다. 복셀 위치를 만드는 옥트리 정보, 밀도, 색상 계수 등이 PyTorch 텐서로 저장된다.

### PLY 파일

3D 데이터를 저장하는 범용 파일 형식이다. 이 프로젝트에서는 브라우저가 PT 파일을 직접 읽지 못하기 때문에 PT의 데이터를 PLY로 풀어서 저장한다.

PLY는 단순한 **데이터 상자**다. PLY 안에 값이 정확히 들어 있어도, 브라우저 렌더러가 그 값을 원본과 다른 방식으로 계산하면 화면은 다르게 보일 수 있다.

### 복셀

3차원 공간의 작은 상자다. 이 모델은 약 475만 개의 복셀로 장면을 표현한다.

### SH, Spherical Harmonics

카메라가 어느 방향에서 보느냐에 따라 복셀 색상을 바꾸기 위한 계수다.

- SH0: 기본 색상
- SH1: 1차 방향 변화
- SH2: 더 복잡한 방향 변화
- SH3: 현재 모델이 가진 최대 방향 표현

SH degree를 높인다고 기하 구조나 해상도가 높아지는 것은 아니다. **방향에 따른 색 표현만 더 정교해진다.**

### 밀도와 알파 합성

한 복셀이 얼마나 불투명한지 계산하는 값이다. 여러 복셀이 한 픽셀에 겹치면 카메라 앞에서 뒤 순서대로 색과 투명도를 누적해야 한다. 순서가 틀리면 검은 틈, 누수, 잘못된 색, popping이 생길 수 있다.

### Morton 정렬

옥트리 공간에서 복셀을 순서대로 나열하는 방법이다. 원본 SVRaster는 단순히 카메라와의 거리만 사용하지 않고, 광선 방향과 화면 타일을 고려한 Morton 순서를 사용한다.

## 3. 원본과 웹 뷰어의 차이

```text
원본 PT
  -> NVIDIA CUDA SVRaster 렌더러
  -> 화면 타일별 방향 의존 Morton 정렬
  -> 각 픽셀에서 front-to-back으로 투명도 누적
  -> 높은 품질의 기준 이미지

변환 PLY
  -> WebGL2 뷰어
  -> 복셀 큐브 475만 개를 한 번에 instanced draw
  -> 전역 정렬 후 일반 알파 블렌딩
  -> 원본과 다른 합성 결과
```

즉, PT와 PLY의 파일 형식 차이보다 **CUDA 원본 렌더러와 WebGL 뷰어의 알고리즘 차이**가 더 크다.

## 4. 테스트 환경과 관찰된 문제

### 데이터

| 항목 | 값 |
|---|---:|
| PT 크기 | 약 943 MB |
| 기존 PLY 크기 | 약 1.1 GB |
| 복셀 수 | 4,754,506 |
| 옥트리 레벨 | 6~16 |
| SH degree | 3 |
| SH rest 계수 | 복셀당 45개 |
| 밀도 코너값 | 복셀당 8개 |

PLY는 압축 포맷이 아니며, 공유되는 밀도 코너값을 각 복셀에 반복 저장한다. 따라서 웹 전송과 메모리 사용 면에서도 효율적이지 않다.

SH3 렌더링에 필요한 주요 GPU 텍스처만 계산해도 약 1.1 GB다. 브라우저에서는 여기에 원본 ArrayBuffer, 파싱 배열, 정렬 배열과 복사본이 추가된다.

### 사용자 육안 관찰

- PT를 원본 렌더러로 렌더링하면 모델 품질이 좋다.
- PLY를 현재 웹 뷰어에서 열면 전체적으로 선명하지 않다.
- 가운데 꽃 부분에 세로 줄처럼 깨지는 현상이 보인다.
- `quality=detail`에서는 검은 크랙이 전체적으로 더 심해졌다.
- SH1과 SH3의 일반 화면 차이는 육안으로 매우 작았다.
- 샘플링 수와 단순 정렬 모드를 바꿔도 차이가 매우 작았다.
- SH 계수 레이아웃 후보 중 기본 모델이 가장 자연스러웠고, 다른 후보는 일부 색상이 잘못 보였다.

이 항목들은 자동 이미지 측정값이 아니라 사용자가 실제 화면을 비교해 기록한 결과다.

## 5. 지금까지 수행한 테스트

### 5.1 PLY 파일이 정상적으로 로드되는지 확인

**질문:** 화질 문제가 파일 경로나 로딩 실패 때문인가?

**방법:** 로컬 PLY를 Vite 서버에서 불러오고 헤더와 복셀 개수를 확인했다.

**결과:** 정상적으로 로드되며 4,754,506개 복셀이 파싱된다.

**의미:** 파일을 못 읽어서 생긴 문제는 아니다.

---

### 5.2 검은 화면과 카메라 문제 수정

**질문:** 모델이 안 보이거나 화면 밖에 있는 문제인가?

**방법:** 셰이더 정밀도 불일치, 하드코딩된 카메라와 씬 변환을 수정했다.

**결과:** 모델이 화면에 정상적으로 표시되었다.

**의미:** 이제 남은 문제는 “표시 여부”가 아니라 “표시 품질”이다.

---

### 5.3 SH1~SH3 계수 개수와 수식 검증

**질문:** SH 색상 계산이 틀려서 색과 품질이 나쁜가?

**방법:** NVIDIA SVRaster 수식과 비교해 다음 항목을 수정하고 단위 테스트를 추가했다.

- SH1 순서와 부호: `-y`, `+z`, `-x`
- SH2의 `yz`, `xz` 항 부호
- SH3의 7개 basis 순서
- degree별 필요한 rest 계수: SH1 9개, SH2 24개, SH3 45개

**자동 테스트 결과:** SH 테스트 5개 모두 통과.

**육안 결과:** SH1과 SH3 일반 화면의 차이는 매우 작았다.

**의미:** SH 수식 오류는 수정되었다. 그러나 SH는 방향성 색상을 바꾸는 요소이므로, SH3를 켜는 것만으로 구조의 선명도나 크랙이 해결되지는 않는다.

---

### 5.4 SH 방향 반전 비교

**질문:** `camera -> voxel`과 `voxel -> camera` 방향을 반대로 해석한 것이 원인인가?

**방법:** 두 방향을 비교하고 차이를 강조하는 heatmap 모드를 추가했다.

**결과:** heatmap에서는 노랑, 주황, 빨강이 많이 나타났다. 이는 두 방향 계산 결과가 실제로 다르다는 뜻이다. 하지만 일반 화면에서 올바른 방향을 사용해도 원본 수준의 화질은 나오지 않았다.

**의미:** heatmap 색은 모델의 실제 색이 아니라 **두 계산의 차이를 과장해 보여주는 디버그 색**이다. 방향 계산은 중요하지만 현재 화질 저하의 유일한 원인은 아니다.

비교 URL:

```text
?compare=viewdir
?sh=3&inspect=direction
```

---

### 5.5 SH1과 SH3 직접 비교

**질문:** PLY에 SH3가 실제로 들어 있고 화면에 반영되는가?

**방법:** 좌우 동기화 비교와 SH1/SH3 차이 heatmap을 추가했다.

**결과:** 계수는 존재하고 계산에도 사용된다. 차이 heatmap에서는 변화가 보이지만 일반 화면의 육안 차이는 작았다.

**의미:** SH3가 무시되는 것은 아니다. 장면의 대부분에서 고차 SH가 만드는 색 차이가 작거나, 다른 렌더링 오차가 더 크게 보이는 상태다.

비교 URL:

```text
?compare=sh13
?sh=3&shDebug=degdiff13
```

---

### 5.6 SH 계수 레이아웃 후보 비교

**질문:** PT의 `_shs` 배열을 PLY로 펼치는 순서가 틀렸는가?

**방법:** 기본, basis-major, transpose 후보 PLY를 만들어 비교했다.

**결과:** 기본 변환 모델이 가장 자연스러웠다. 다른 두 후보는 일부 영역의 색상에 문제가 있었다.

**의미:** 현재 기본 레이아웃이 가장 타당하다. 무작정 SH 배열 순서를 바꾸는 것은 해결책이 아니다.

---

### 5.7 PT와 PLY의 위치 및 SH 값 수치 비교

**질문:** PLY로 변환하는 순간 숫자가 크게 손실되는가?

**방법:** 전체 모델에서 균일하게 고른 복셀 100,000개를 PT와 PLY에서 직접 비교했다.

| 비교 항목 | 결과 |
|---|---:|
| 위치 최대 절대 오차 | `3.7551e-6` |
| octlevel 불일치 | 0개 |
| SH0 최대 절대 오차 | 0 |
| SH1~SH3 rest 최대 절대 오차 | 0 |
| 확인한 PLY 밀도값 | 800,000개 |
| PT 원본 밀도값과 정확히 일치 | 800,000개 |

**결과:** 위치 오차는 매우 작고 SH 값은 표본에서 완전히 동일했다. 확인한 밀도 숫자도 모두 PT에 존재하는 값이었다.

**의미:** “PLY가 SH 색상 숫자를 망가뜨려서 화질이 나빠졌다”는 가설은 가능성이 낮다.

**주의:** 이 테스트는 각 밀도 숫자가 PT에 존재하는지는 확인했지만, 8개 코너 각각이 정확한 공간 좌표에 연결되었는지 전체 모델에 대해 증명한 것은 아니다. 이 부분은 추가 검증 가치가 있다.

---

### 5.8 샘플 수 비교

**질문:** 한 복셀 내부를 너무 적게 샘플링해서 줄무늬가 생기는가?

**방법:** 샘플 수를 바꾸고, 8회 jitter 방식과 원본에 가까운 3회 midpoint 방식을 비교했다.

```text
?sh=3
?sh=3&integrationMode=jittered&samples=8
?sh=3&samples=8
?quality=detail
```

**결과:** 일반 화면 차이는 매우 작았다. `quality=detail`은 오히려 검은 크랙을 더 심하게 만들었다.

**의미:** 샘플 수 부족이 주원인이라면 3회와 8회에서 눈에 띄는 개선이 있어야 한다. 실제 차이가 작았으므로 샘플 수만 계속 올리는 것은 효과가 낮고 성능만 크게 떨어뜨릴 가능성이 높다.

---

### 5.9 광선과 복셀 상자의 교차 계산 비교

**질문:** 광선이 복셀 안으로 들어가고 나오는 위치를 잘못 계산하는가?

**방법:** 기존 교차 계산과 평행 광선을 안전하게 처리하는 exact slab 계산을 비교했다. 로컬 좌표에서 trilinear 밀도 보간도 수정했다.

```text
?sh=3
?sh=3&rayMode=legacy
```

**결과:** 차이는 육안으로 매우 작았다.

**의미:** 광선 교차 계산의 안정성은 개선되었지만 전체 화질 문제의 주원인은 아니었다.

---

### 5.10 거리 정렬과 view-depth 정렬 비교

**질문:** 카메라에서 복셀까지의 단순 거리를 사용해서 합성 순서가 틀리는가?

**방법:** 기존 Euclidean distance 정렬과 카메라 전방축 투영 깊이 정렬을 비교했다.

```text
?sh=3
?sh=3&sortMode=distance
```

**결과:** 육안 차이가 거의 없었다.

**의미:** 두 전역 정렬 방식은 이 장면에서 비슷한 순서를 만들었다. 하지만 이것이 “정렬은 문제가 없다”는 뜻은 아니다. 원본은 전역 정렬이 아니라 **화면 타일과 광선 방향에 따라 다른 순서**를 사용한다.

---

### 5.11 WebGL MSAA 경계 테스트

**질문:** 브라우저가 큐브 모서리를 반투명하게 안티앨리어싱해서 검은 선을 만드는가?

**방법:** proxy cube의 raster MSAA를 기본적으로 끄고 기존 방식과 비교 가능하게 했다.

```text
?sh=3
?sh=3&rasterAA=on
```

**현재 상태:** 기능 구현과 빌드는 완료되었다. 하지만 두 화면에 대한 최종 사용자 판정과 고정 스크린샷은 리포트에 기록되지 않았다.

**의미:** 아직 성공 또는 실패로 결론 내리면 안 되는 항목이다.

---

### 5.12 front-to-back 합성 테스트

**질문:** 기존 back-to-front 알파 블렌딩 대신 원본과 같은 방향으로 누적하면 개선되는가?

**방법:** 전역 depth 정렬을 뒤집고 destination alpha를 이용한 front-to-back 블렌딩을 추가했다.

```text
?sh=3&compositeMode=front
```

**현재 상태:** 구현 및 자동 빌드는 완료되었다. 최종 고정 화면 비교 결과는 기록되지 않았다.

**한계:** 원본처럼 픽셀마다 정확한 순서를 계산하는 방식이 아니라, 하나의 전역 순서를 사용한 근사 테스트다.

---

### 5.13 48비트 Morton 정렬 테스트

**질문:** 원본 SVRaster의 방향 의존 Morton 순서를 사용하면 크랙과 합성 오류가 줄어드는가?

**발견된 문제:** 기존 PLY의 `octpath`는 `uint32`로 저장되었다. 원본 값은 최대 48비트가 필요하며, 표본 100,000개 모두 32비트 범위를 초과했다.

**수정:**

- 새 변환기는 `octpath_low`, `octpath_high`로 나누어 48비트를 보존한다.
- 기존 PLY는 위치와 octlevel에서 전체 octpath를 복원한다.
- 원본의 `octpath XOR repeated quadrant` rank를 구현했다.
- 16비트 radix sort 3회로 48비트 값을 정렬한다.

```text
?sh=3&sortMode=morton
```

**자동 테스트 결과:** Morton 및 정렬 테스트 5개 모두 통과. 475만 복셀 크기의 합성 배열 벤치마크에서 정렬 약 380 ms.

**현재 상태:** 기능 구현은 완료되었지만 최종 육안 비교 결과는 기록되지 않았다.

**한계:** 현재 구현은 global Morton이다. 원본의 화면 타일별 Morton 정렬과 픽셀별 누적을 완전히 재현하지 않는다.

## 6. 자동 검증 결과

2026-07-23에 현재 작업 트리에서 다시 실행했다.

```text
npm run build       PASS
npm run test:sh     PASS, 5/5
npm run test:sort   PASS, 5/5
```

자동 테스트가 통과했다는 것은 구현한 수식과 작은 입력의 정렬 동작이 예상과 일치한다는 뜻이다. **실제 화면이 원본과 같은 품질이라는 뜻은 아니다.**

## 7. 현재 확정할 수 있는 결론

### 결론 A: SH degree를 올리는 것만으로는 해결되지 않는다

SH1~SH3 계산은 수정되고 테스트되었다. SH3도 실제로 사용된다. 그러나 SH는 방향성 색상을 담당하므로 흐린 구조, 크랙, 누수 문제를 직접 해결하지 못한다.

### 결론 B: 샘플 수를 계속 올리는 것은 우선순위가 낮다

3회 midpoint와 8회 jitter 결과 차이가 작았다. 더 높은 샘플 수는 현재 3~7 FPS 수준의 성능을 더 낮출 수 있다.

### 결론 C: 기존 PLY의 주요 숫자는 보존되어 있다

표본 비교에서 위치, SH0, SH1~SH3 값이 PT와 일치했다. 따라서 PLY 변환이 모든 품질 정보를 없앴다고 보기는 어렵다.

다만 기존 PLY의 48비트 octpath는 32비트로 잘렸다. 이는 정확한 원본 정렬을 구현할 때 문제가 되며 새 변환기에서는 수정되었다.

### 결론 D: 현재 가장 큰 차이는 렌더링 구조다

원본은 화면 타일별로 방향 의존 순서를 만들고 픽셀별 front-to-back transmittance를 누적한다. 현재 WebGL 뷰어는 수백만 개의 proxy cube를 하나의 전역 순서로 그린다.

전역 정렬은 모든 픽셀에서 동시에 정확할 수 없다. 특히 크기가 다른 적응형 복셀이 겹치는 경계에서는 잘못된 순서가 생길 수 있다.

### 결론 E: 현재 방식은 원본 화질 재현용으로 부족하다

현재 PLY는 브라우저에서 읽을 수 있다는 장점은 있지만 다음 문제가 있다.

- 파일이 크고 압축되지 않는다.
- GPU와 CPU 메모리 사용량이 매우 크다.
- 원본의 공간 구조와 렌더링 순서를 그대로 사용하지 못한다.
- 현재 WebGL2 합성 방식으로는 PT 원본 렌더 품질을 보장할 수 없다.

따라서 “PLY 변환이 완전히 무의미하다”보다는 다음 문장이 기술적으로 더 정확하다.

> PLY 변환은 데이터를 브라우저로 전달하는 데는 성공했지만, 현재 WebGL 렌더링 구조로는 원본 SVRaster 모델의 시각 품질을 재현하지 못했다.

## 8. 이 리포트에서 아직 약한 부분

현재 리포트에는 코드 검증과 사용자 육안 관찰은 있지만, 같은 카메라에서 원본과 웹 결과를 픽셀 단위로 비교한 정량 자료가 없다.

다음 항목은 아직 확정되지 않았다.

- 원본 CUDA와 WebGL이 정확히 같은 카메라 pose를 사용한 비교
- 원본 이미지와 웹 캡처의 PSNR, SSIM 및 difference image
- 8개 밀도 코너값이 모든 복셀에서 정확한 공간 코너에 연결되었는지 검증
- MSAA off/on의 고정 화면 비교 결과
- depth/front와 global Morton/front의 고정 화면 비교 결과
- 원본과 같은 tile-based Morton을 구현했을 때의 결과
- 픽셀별 정확한 front-to-back 누적을 구현했을 때의 결과

따라서 현재 결론은 충분히 합리적이지만, 외부 발표나 기술 의사결정 자료로 쓰려면 최소한 고정 카메라 정량 비교를 추가하는 편이 좋다.

## 9. 리포트를 강화하기 위한 추가 테스트

### 우선순위 1: 같은 카메라로 원본과 웹 화면 비교

가장 가치가 높은 테스트다.

1. 원본 CUDA 렌더러에서 카메라 위치, 회전, FOV, 해상도를 저장한다.
2. WebGL 카메라에 같은 값을 입력한다.
3. 두 결과를 PNG로 저장한다.
4. 좌우 이미지와 절대 차이 이미지를 한 장으로 만든다.

이 테스트가 있어야 “느낌상 나쁘다”가 아니라 “어느 픽셀에서 얼마나 다르다”라고 설명할 수 있다.

### 우선순위 2: PSNR과 SSIM 측정

- PSNR: 픽셀 색 오차가 얼마나 큰지 나타낸다. 높을수록 비슷하다.
- SSIM: 구조와 명암 패턴이 얼마나 비슷한지 나타낸다. 1에 가까울수록 비슷하다.

`fused-ssim` CUDA 확장은 필요 없다. 리포트용 비교는 CPU 기반 `scikit-image` 또는 별도 간단한 이미지 비교 코드로 충분하다.

### 우선순위 3: 밀도 코너 연결 검증

현재는 PLY 밀도 숫자가 PT에 존재한다는 것만 확인했다. 다음에는 임의의 복셀을 뽑아 각 코너의 3D grid key를 재구성하고, PT의 `_geo_grid_pts[vox_key]`와 PLY의 `grid0~7_value`를 같은 코너끼리 비교해야 한다.

이 테스트에서 코너 순서가 틀린 것으로 나오면 세로 줄과 밀도 깨짐의 직접 원인이 될 수 있다.

### 우선순위 4: 아직 결과가 없는 세 가지 URL 고정 캡처

카메라를 움직이지 않고 다음 세 화면을 캡처한다.

```text
# 기준
http://localhost:5173/?sh=3

# 전역 front-to-back
http://localhost:5173/?sh=3&compositeMode=front

# global Morton + front-to-back
http://localhost:5173/?sh=3&sortMode=morton
```

MSAA도 별도로 비교한다.

```text
http://localhost:5173/?sh=3&rasterAA=on
```

비교할 위치는 꽃의 세로 줄, 화분 경계, 자전거 바퀴, 배경의 검은 크랙이다.

### 우선순위 5: 새 48비트 PLY 재생성

기존 PLY는 octpath가 잘려 있다. 뷰어가 위치에서 이를 복원할 수는 있지만, 최종 검증용 파일은 새 변환기로 다시 만드는 것이 안전하다.

```bash
.venv/bin/python scripts/convert_to_ply.py \
  models/SVRaster/bonsai_og/checkpoints/iter020000_model.pt \
  models/SVRaster/bonsai_og/checkpoints/iter020000_model_48bit.ply
```

새 파일 헤더에는 `octpath_low`, `octpath_high`가 있어야 한다.

## 10. 추가 개발을 계속한다면

### 선택지 A: WebGL2에서 tile-based 렌더러 재구현

화면을 작은 타일로 나누고 각 타일에 영향을 주는 복셀 목록을 만든 뒤, 타일별 Morton 순서로 렌더링한다.

- 장점: 현재 코드와 WebGL2를 유지할 수 있다.
- 단점: 복셀 중복 목록, 다중 draw, 메모리 및 성능 문제가 크다.
- 난이도: 높음.

### 선택지 B: WebGPU compute 기반으로 재작성

GPU compute shader에서 타일 목록과 픽셀별 transmittance를 계산한다.

- 장점: 원본 CUDA 알고리즘에 더 가까운 구조를 만들 수 있다.
- 단점: 렌더러 핵심을 대부분 다시 작성해야 한다.
- 난이도: 매우 높음.

### 선택지 C: 서버에서 원본 렌더러 실행

브라우저는 카메라 정보만 보내고, CUDA 서버가 원본 방식으로 이미지를 렌더링해 스트리밍한다.

- 장점: 원본 품질을 가장 빨리 유지할 수 있다.
- 단점: GPU 서버 비용, 네트워크 지연, 오프라인 사용 불가.
- 적합한 경우: 브라우저 내부 계산보다 정확한 품질이 더 중요한 서비스.

### 선택지 D: PLY 대신 전용 바이너리 포맷 사용

octpath, octlevel, 공유 grid point, SH 계수를 원래 구조에 가깝게 저장하고 chunk 단위로 로드한다.

- 장점: 파일 크기와 메모리 중복을 줄일 수 있다.
- 단점: 전용 로더와 버전 관리가 필요하다.
- 주의: 파일 포맷만 바꿔서는 합성 알고리즘 문제가 해결되지 않는다.

## 11. 권장 의사결정

### 목표가 “빠른 웹 미리보기”라면

현재 뷰어를 유지하되 원본과 동일하지 않은 근사 결과임을 명시한다. SH나 샘플 수 미세 조정에 더 많은 시간을 쓰는 것은 권장하지 않는다.

### 목표가 “PT 원본과 같은 품질의 웹 뷰어”라면

현재 렌더링 구조를 계속 보정하는 것보다 tile-based 또는 WebGPU 렌더러를 별도 프로젝트로 설계하는 편이 타당하다.

개발을 결정하기 전에 다음 세 가지를 먼저 완료하는 것이 좋다.

1. 동일 카메라 원본/WebGL 캡처
2. PSNR/SSIM/difference image
3. 밀도 코너 연결 검증

이 세 결과가 있으면 렌더러를 다시 작성할 가치와 예상 개선 범위를 더 객관적으로 판단할 수 있다.
